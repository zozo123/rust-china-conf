# 百万次编译，一小时机器人

[English](talk-25min.en.md) · [舞台手册](runbook-6min.md) · [幻灯片提纲](slides.md)

**25 分钟演讲提示，包含六分钟演示，另留五分钟问答。**
以下时间是彩排预算。标题表达动机，并不表示已经测得编译次数与机器人时间的换算关系。

## 0:00–2:00 · 机器人成功了

[打开植入缺陷的回放，同时展示任务与契约两个结论。]

> “机器人举起了方块，仿真器报告任务成功。
> 这个改动值得信任吗？
>
> 看一下时间戳：每段运动使用的观测都已经过期 600 ms，而我们的策略上限是 250 ms。
>
> 任务成功了，契约却失败了。”

[停顿，让观众看清两个结论。]

“这是 robosuite 和 MuJoCo 中的 Panda 机械臂。仿真让我们能够重复这个错误。
实体硬件验证属于后续阶段。今天的问题是：一个代码改动怎样才能进入下一阶段？”

## 2:00–5:00 · Rust 决定什么

[展示简短的决策逻辑与 250/251 ms 边界测试。]

“控制器提出接近、下降、抓取、举起四段运动，Rust 决定每段能否开始。
仿真停止信号优先；未来时间戳无效；超过策略年龄的观测必须拒绝。

我们故意植入了一个很小的缺陷：缺少时效检查。编译成功不能证明这项行为属性，
方块成功举起也不能。契约测试提出了另一个必须回答的问题。”

解释：观测年龄等于仿真时间减去采集时间。桥接程序推进仿真时钟，同时交付历史观测；
不是让仿真暂停，再靠等待制造“过期”。

“这里有一个重要边界：授权发生在每段运动派发时。一段运动可以包含多个控制步。
我们没有演示连续的物理安全监督。250 ms 是演示用的策略阈值，不是硬件安全限。”

## 5:00–8:00 · 候选改动需要独立检查

[展示工单、允许修改的路径和受保护测试。]

“智能体提出实现改动，但不能重新定义什么叫通过。
候选补丁只能修改决策门实现，不能修改验收测试、仿真器或校验器。

我们保留失败轨迹、基线修订和补丁。校验器要求必需场景完整，派发必须有匹配的授权，
导出的二进制必须与记录的摘要一致。缺失证据不能算通过。”

摘要标识一个产物，不能认证整段执行历史，也不能证明程序普遍正确。
受信任的编排与受保护检查仍属于证据边界。

“仓库中的自动彩排默认使用已审阅的回退补丁，也接受外部智能体产生的补丁。
脚本本身不调用大语言模型。”
现场使用外部智能体时要明确展示，并把单次尝试的等待上限设为约 45 秒；超时就直接切到已审阅的回退补丁，并在应用前说明。

## 8:00–11:00 · 临时工作区与 Incredibuild

[展示运行器、编译服务、验证三个职责。]

“每个候选改动都要重新验证。我们也希望执行环境是临时的：
从干净状态开始，尝试改动，导出证据，然后删除工作区。

工作区可以丢弃，符合条件的编译成果可以由构建服务复用。
但这个候选版本的测试结论，必须重新取得。”

“Cargo 通过 Incredibuild Linux 包装程序构建，并使用 rustc 配置。
预期收益来自分布式编译和有效结果复用。测试与仿真单独执行。
要声称辅助机做了工作或缓存被复用，就需要相应的测量证据。”

“这是 Rust 大会，所以证明路径也由 Rust 负责。`swf-cli` 解析 Build History
与缓存统计。只要某个 IB 样本的远程任务为零、远程核时为零、计数有歧义，
或者父修订预热路径没有缓存命中，整次证明就失败。Python 只是 robosuite
适配器；它可以提出运动，不能授权运动，也不能认证构建。”

[部署标注：当前使用 EC2 工作区；islo 提供方计划接入。]

“当前实现是在已有 Linux 主机上创建独立 Git 工作区和全新 Cargo 输出目录。
删除工作区不会销毁主机，也不构成虚拟机隔离。islo 是未来计划接入的运行器提供方，
已经验证的执行发生在 EC2 网格上。”

提供方说明控制在 30 秒内，不展开配额和余额插曲。

## 11:00–17:00 · 六分钟演示

按[舞台手册](runbook-6min.md)执行六个动作：

1. 植入缺陷的程序举起方块：任务完成，时效契约失败。
2. 审查受约束的补丁。
3. 导出改动并删除工作区 A。
4. B 检出记录的基线，使用全新输出构建。
5. 修复后：陈旧请求零派发，新鲜请求举起方块。
6. 展示证据与可执行文件身份。

回放时明确说“这是记录”。实时运行展示自己的编号和结果。
彩排的完整矩阵与现场选跑的两个用例必须分别标注。
不能把历史 88/88 当作当前校验器的新结果。

## 17:00–20:00 · 测量说明了什么

[展示两次历史观测，明确标注为历史数据，并标明运行编号。]

“A 的构建阶段用时 21.426 秒，B 用时 21.948 秒，B 慢了 522 ms。
两个记录均标明使用 Incredibuild。

这说明集成路径在两个工作区中运行过，不能证明加速、缓存复用或辅助机实际执行。
历史记录里的 cold/warm 是阶段名称，不是经过控制的缓存状态。”

“现在的实验工具使用同一固定候选版本，对比原生 Cargo、显式清空用户缓存后的 IB，
以及先由父修订填充该缓存再构建候选的 IB。它轮换运行顺序，每种模式至少五次。
只有每个 IB 样本证明辅助机工作、每个热样本证明缓存命中之后，
Rust 校验器才报告中位数与范围。在 EC2 产生这份收据之前，性能收益仍标记为未测量。”

分别测量创建环境、检出、智能体响应、编译、测试、仿真和导出。
编译变快未必主导整个候选周期；在没有实测这些量之前，不能把它换算为成本节省或机器人工时。

## 20:00–23:00 · 保留下来的证据

[展示简洁的证据摘要，再回到两个机器人结论。]

“有用的交付物是改动及其证据：源码身份、补丁、实际可执行文件、场景结果，
以及提案、决策、派发的轨迹。

归档的 Linux 运行包含 17 个回合：10 次举起、5 次陈旧拒绝、
1 次仿真停止、1 次超时。原校验器报告 88/88。
当前加强后的检查范围不同，必须产生自己的结论。”

历史二进制未提交到仓库，只保留摘要和日志。
新彩排会导出自己的可执行文件，以便核验。

“修复后的程序拒绝旧观测，也能在新鲜观测下完成任务。这才是行为上的结果。”

## 问答与来源

- **为什么 Rust？** 小型、带类型的决策接口与确定性的时钟输入使契约明确且易测。
  Rust 不会自动保证时效策略正确。
- **为什么机器人？** 任务成功与策略符合可以直观地不同。仿真提供可重复任务，不占用实体硬件。
- **IB 加速什么？** 符合条件的编译；不是模型推理、仿真物理或缓存的验收结论。
- **为什么 islo？** 未来实现一次性执行职责的提供方，当前演示部署使用 EC2。
- **为什么没有加速数字？** 本次是每阶段一次观测的流程演示，受控对照仍待执行。

历史数字均来自[归档证据](../examples/README.md)中的
`ec2-e2e-20260923-160725`。引用时保留可见的运行编号。

20 分钟版本缩短架构与证据讨论，保留行为对比、演示、实测计时和范围说明。
